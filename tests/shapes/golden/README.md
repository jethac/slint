# Golden vector format and tolerance policy

Generated by `../generate.sh` from the pinned androidx sources
(`23327507f7fc7d5b19d65fec4b090f60c970079b`). Every f32 is stored as its
unsigned IEEE-754 bit pattern (u32), so exact bit-for-bit comparison is
possible.

## `material_shapes.json`

```json
{
  "pin": "<androidx commit>",
  "shapes": {
    "<name>": {
      "cubics": [[8 × u32] × n],
      "features": [{"kind": "edge"|"corner", "convex": bool, "count": int}],
      "center": [u32, u32],
      "bounds": [u32 × 4],
      "max_bounds": [u32 × 4]
    }
  }
}
```

`cubics` are the cubic anchor/control points in order
(`anchor0 x/y, control0 x/y, control1 x/y, anchor1 x/y`). `bounds` is
`calculateBounds(approximate = true)`, `max_bounds` is `calculateMaxBounds()`.

## `morphs.json`

```json
{"pin": "<androidx commit>", "morphs": {"<from>-><to>": {"<t>": [[8 × u32] × n]}}}
```

with `t` ∈ {0, 0.25, 0.5, 0.75, 1}.

## Tolerance policy (per issue #6 review)

- Values computed without transcendental functions or square roots (linear
  interpolation, structure bookkeeping, feature/cubic counts, centers) must be
  **bit-exact**.
- Everything else — anything that went through `sin`/`cos`/`atan2`/`sqrt` —
  must be within **1e-4 absolute**. The JVM's `StrictMath`-backed intrinsics and
  the Rust `no_std`/`libm` implementations are allowed to round the last ulp
  differently; on the `std` target Rust uses the platform `libm`, which in
  practice matches the JVM bit-for-bit for these inputs.

`internal/core/tests/shapes_parity.rs` enforces the 1e-4 bound on all cubic
anchors, centers and bounds, and exact equality on cubic/feature counts,
feature kinds, convexity, and the shape center.
